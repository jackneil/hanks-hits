VERDICT: NEEDS ATTENTION

- **CRITICAL:** The beacon guard compares incompatible identities. The plan defines the persisted marker as the authenticated user ID (`...html:581-589`), but defines distinct `ownerId` and per-epoch `ownerToken` (`...html:625-629`, `:648-649`). The guard compares `ownerToken` to the marker (`...html:657-661`). This suppresses normal READY beacons and can lose unsaved progress. Compare `ownerId` to the marker, independently validate token and epoch, and add a positive READY-beacon test.

- **CRITICAL:** Cross-tab owner-marker changes do not invalidate existing coordinators. The plan only wires invalidation to sign-out broadcast (`...html:650`); current code listens only to `SIGNOUT_BROADCAST_KEY` (`apps/web/src/shared/hooks/useAuthSync.ts:102-110`). A second tab can claim user B while a READY user-A coordinator remains active and posts A’s in-memory data under B’s session. Add marker-change/owner-claim broadcasting or listening, synchronous invalidation, pagehide purge, and a two-tab regression test.

- **CRITICAL:** Typed response correlation has no specified wire path. Responses require `requestId` and `logicalSaveId` (`...html:713-728`), while `RequestSnapshot.canonicalBody` contains only `{data, merge:true}` (`...html:456-465`) and the route protocol validates only `data` and `merge` (`...html:748-752`). Current client and route likewise send/accept only those fields (`useAuthSync.ts:120-146`, `route.ts:128-132`). Define exact request/response propagation, including beacon payloads, and mismatch tests that cannot acknowledge stale requests.

- **MEDIUM:** Bootstrap merge mode is contradictory. `RequestSnapshot` hardcodes `merge:true` (`...html:458`), but the current bootstrap path uses `merge:false` (`useAuthSync.ts:283-287`), and the plan never assigns a merge mode to bootstrap snapshots. Add explicit merge mode to the snapshot and assert its canonical bytes, logical ID, and acknowledgment.

- **MEDIUM:** Retry-After precedence is undefined. The plan requires both an exact backoff schedule (`...html:605`, `:677`) and honoring `Retry-After` (`...html:682-689`), but does not say whether the effective delay is the header, schedule, maximum, or minimum. Specify the formula, clamping, HTTP-date clock, and tests for every retry phase.

- **MEDIUM:** Successful normal POST response adoption is underspecified. The plan updates the clean baseline from canonical response data (`...html:619`) but only specifies guarded live adoption for re-fetches (`...html:602`). It does not define what happens when server merge changes response data or when S1 changes during POST. Specify live-adoption versus preservation, guards, baseline, acknowledgment, and queue behavior, with a differing-response/S1 test.

- **MEDIUM:** Chess migration can pass with a canonical-shaped fake legacy fixture. The plan requires nonzero legacy fields but does not define the legacy raw schema or mapping (`...html:510-511`). Current source only identifies `chess-storage` as a legacy key (`storage-keys.ts:20-21`) and implements the current `hank-chess-state` shape (`games/chess/lib/store.ts:406-441`). Define exact legacy bytes, projection, malformed fallback, and canonical write-back tests.

- **MEDIUM:** Inventory and inspection tests can be green while production caller wiring is wrong. The plan proves source-set equality (`...html:513-514`, `:560-563`), but defines no typed runtime inventory entry binding caller `getState/setState` to its adapter. The probe also has no required path from a mounted production hook to the inspected coordinator (`...html:730-744`; current hook API `useAuthSync.ts:17-23`). Require real-caller mounting through the production factory and probe assertions on that same coordinator.
