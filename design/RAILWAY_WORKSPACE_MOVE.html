Moving Hank's Hits to the personal Railway workspace

Runbook: project hanks-hits, HANK.ai workspace → Jack (PERSONAL). Written 2026-09-02. Every claim below was verified against the live Railway API, not read off a docs page.

Verdict. Railway supports the move as a first-class operation, it keeps the same project ID, and it is reversible. It takes about one second.

But: Railway refuses to transfer a project that owns object-storage buckets, and hanks-hits owns two (app-files with the 910 ROM files, and Postgres-PITR). Deleting a bucket does not clear the block immediately: the bucket record survives a retention window of roughly two days, and the block survives with it. So the calendar cost is about 48 hours, and the real work is decoupling the ROM library from a bucket that has to die.

Shape of the plan: move the ROM library into a sidecar storage project in the personal workspace first (the same pattern already used for passerjack-storage), then drop both buckets, wait out the retention window, then transfer.

What is in the project today

Both workspaces are on the Pro plan with an active payment method, and the account is a workspace-level member of both, so the plan and permission preconditions for a transfer are already satisfied. Personal holds 10 of its 100 project slots.

The blocker, verified

Rather than trusting forum posts, three throwaway projects were created in HANK.ai and driven through the real mutation:

  • Project with a bucket → transfer refused. Verbatim API response: Cannot transfer a project that has object storage buckets. Please delete all buckets in this project before transferring.
  • Bucket deleted, transfer retried immediately → still refused, same message. The bucket record is still attached to the project (project.buckets still returns it, deletedAt still null) even though railway bucket list reports the environment as empty. That gap is the retention window.
  • Project with no bucket → transferred in one call, HANK.ai → personal and back again, same project ID both ways. So the move itself is trivial and reversible.

Two probe projects were deleted afterwards. One was deliberately kept: zz-xfer-probe-retention (96e713b2-7923-49c9-a8d2-55a2fea68bd8), whose bucket was deleted at 2026-09-02 11:58 UTC. It is a canary. When it becomes transferable, the real retention window is known, and the same clock can be trusted for hanks-hits. Delete it once the move is done.

Prior art: passerjack

The same wall was clearly hit a few days ago. passerjack-storage was created 2026-08-29 13:33 UTC with a bucket passerjack-blobs-east one minute later, and passerjack only got a fresh bucket (passerjack-blobs) on 2026-09-01 09:51 UTC. That is a sidecar storage project standing in during a roughly 68-hour gap. This plan is that pattern, done deliberately.

Plan

Phase 0Capture and back up (about 30 minutes)

  1. Dump every service variable to a local, gitignored file. These values exist nowhere in the repo, and AUTH_SECRET in particular is invisible to a process.env grep because next-auth reads it implicitly. Sessions are 30-day JWTs, so losing it signs out every kid. 
    cd ~/Github/hanks-hits
mkdir -p ~/railway-backup/hanks-hits
for s in hanks-garage Postgres webserver url-cache; do
  railway variables --service "$s" --json > ~/railway-backup/hanks-hits/vars-$s.json
done
  2. Dump the database and prove the dump restores. Do not trust an exit code. 
    URL=$(railway variables --service Postgres --json | jq -r .DATABASE_PUBLIC_URL)
PGCONNECT_TIMEOUT=60 pg_dump "$URL" -Fc -f ~/railway-backup/hanks-hits/pre-move.dump
createdb hh_restore_check
pg_restore -d hh_restore_check ~/railway-backup/hanks-hits/pre-move.dump
psql hh_restore_check -c "select relname, n_live_tup from pg_stat_user_tables order by n_live_tup desc"
# compare those counts against the same query on the live database
    Note: the TCP proxy accepted a connection but psql needed a long timeout on first contact. If it still stalls, dump from inside the container with railway ssh instead.
  3. Mirror the ROM bucket to local disk and count the objects. 
    railway bucket credentials --bucket app-files --json   # endpoint, bucket name, key id, secret
aws s3 sync s3://<bucket-name>/ ~/railway-backup/hanks-hits/app-files/ \
  --endpoint-url https://t3.storageapi.dev
find ~/railway-backup/hanks-hits/app-files -type f | wc -l   # expect 910

Phase 1Move the ROM library out of the project (about 30 minutes)

  1. Create hanks-hits-storage in the personal workspace and a bucket in it (region iad, matching the current one). This project holds no services, so it never blocks anything.
  2. Upload the mirrored ROMs into the new bucket, then confirm the object count matches 910.
  3. Repoint the webserver service at the new bucket. It reads two parallel sets of credentials, and both must change: AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_ENDPOINT_URL, AWS_S3_BUCKET_NAME, and CDN_BUCKET_ACCESS_KEY_ID_roms_us, CDN_BUCKET_SECRET_ACCESS_KEY_roms_us, CDN_BUCKET_ENDPOINT_roms_us, CDN_BUCKET_NAME_roms_us. Leave CDN_BUCKET_PUBLIC_NAMES, CDN_BUCKET_REGION_ALIASES and CDN_URL_CACHE_REDIS alone.
  4. Redeploy webserver, then prove a ROM actually loads: open the retro arcade and start a SNES game, and check curl -sI https://cdn-hankshits.up.railway.app/roms/<known-rom>. The service domain does not change, so nothing in the app code needs editing.

Phase 2Clear the gate (about 15 minutes, then wait)

  1. Disable point-in-time recovery on the Postgres service. Railway stages a patch that strips the WAL_ARCHIVE_* variables and deletes the Postgres-PITR bucket; the patch only applies when it is deployed, and that deploy restarts Postgres. Expect a short interruption, so do it late in the evening. The existing recovery history is destroyed and does not come back: a re-enabled PITR window starts from its first new base backup, never retroactively. That is why Phase 0 takes a real dump.
  2. Delete the app-files bucket: railway bucket delete --bucket app-files --yes.
  3. Poll until the project genuinely owns no buckets. The CLI list goes empty immediately and is misleading, so query the API instead: 
    curl -s https://backboard.railway.com/graphql/v2 \
  -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" \
  -d '{"query":"query{project(id:\"08bfe3ff-3cf6-429c-a4f9-16dd711e74af\"){buckets{edges{node{id name deletedAt}}}}}"}'
    An empty edges array is the go signal. Expect roughly 48 hours, and use the zz-xfer-probe-retention canary as the early warning.

Phase 3Transfer (one second)

Dashboard: project canvas → Settings → Transfer Project → pick Jack (PERSONAL). If the modal shows no workspace list, that is a permissions symptom, not a bug. The API path is equivalent and was the one exercised on the probes:

curl -s https://backboard.railway.com/graphql/v2 \
  -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" \
  -d '{"query":"mutation($p:String!,$i:ProjectTransferInput!){projectTransfer(projectId:$p,input:$i)}",
       "variables":{"p":"08bfe3ff-3cf6-429c-a4f9-16dd711e74af",
                    "i":{"workspaceId":"3c5e9ba1-d50b-43be-a4e8-a3f0a5f26912"}}}'

Confirm with railway status, which should now print Workspace: Jack (PERSONAL).

Phase 4Restore and verify (about 30 minutes)

  1. Re-enable point-in-time recovery on Postgres. A new Postgres-PITR bucket appears in the personal workspace, and the recovery window starts from zero.
  2. Leave the ROM library in hanks-hits-storage. Pulling it back into the main project would only re-arm the same blocker the next time anything needs to move.
  3. Run every gate below before calling it done.

Verification gates

The healthcheck path is /, and that page is a filesystem scan that never touches the database. A green deploy therefore proves nothing about login or saves. Check these by hand:

  • Site: https://hankshits.com loads over HTTPS with a valid certificate, not just a 200.
  • Database: sign in with a real account and confirm a saved score round-trips after a reload. Compare table row counts against the Phase 0 numbers.
  • ROMs: start a SNES game and an Atari game. Watch the server log for ROM proxy: CDN redirect rejected (host: ...), which would mean the signed-URL host moved off storage.railway.app and apps/web/src/lib/rom-redirect.ts:5 needs updating.
  • Autodeploy: push a trivial commit to master and confirm hanks-garage builds. If the service shows "Auto deploy unavailable", reconnect the repo in service settings.
  • Billing: new usage lands on the personal workspace. Current project burn is a few dollars a month, so this is a rounding error either way.
  • Cleanup: delete the zz-xfer-probe-retention canary project.

Repo-side impact

Almost none. No project ID, workspace name, or *.railway.internal hostname appears in shipping code, and railway.toml plus the Dockerfile are fully portable. Two constants are worth knowing about:

  • apps/web/src/app/api/roms/[...path]/route.ts:7 hardcodes https://cdn-hankshits.up.railway.app/roms. Safe as long as the webserver service is never recreated, which this plan avoids.
  • apps/web/src/lib/rom-redirect.ts:5 pins the redirect allowlist to storage.railway.app. Re-verify after the new bucket is live.

.claude/commands/release.md pins the project name, project ID and service name, and never names a workspace, so it stays accurate after the move. No repo change is required by the transfer itself.

Risks and open questions

  • Retention length is measured, not promised. Railway describes the bucket deletion window as a safety measure that cannot be expedited. The passerjack timeline suggests roughly 68 hours; the canary will give an exact number.
  • Custom domain behaviour across a transfer is undocumented. Nothing suggests it breaks, and the domain record moves with the project, but the certificate is worth checking within a minute of the transfer.
  • The GitHub binding is the most plausible silent casualty. The known failure mode is a project reporting that no member has access to the repository after its membership set changes. One test push settles it.
  • Unrelated, but noticed: the Railway-purchased domain hijack.observer sits in HANK.ai while the hijack project lives in personal and serves hijackmac.com. Railway does not move purchased domains between workspaces, so that one is stranded. Worth deciding whether to keep paying for it.

Fallbacks

  • Rebuild instead of transfer. Create a fresh project in the personal workspace, redeploy from GitHub, restore the dump, re-add the domain. No waiting, but it means downtime, a new project ID, a DNS cutover, and re-entering every secret. Strictly worse here.
  • Ask Railway to force it. Support has refused this for other users, twice, on the grounds that the deletion window protects against accidental data loss. Worth an ask, not worth planning around.
