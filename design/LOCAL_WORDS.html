Local words: Part C implementation contract

Revised 2026-10-02 after planning review. B1 and the cloud preservation prerequisite are deployed. Client integration and the separately authorized sanitization cutover remain unfinished. This is a product privacy and preservation contract, not a legal compliance determination. It supersedes the prior plan's claims about legal exceptions and guaranteed device capture after a waiting period.

1. Scope and order

Keep player-entered words and drawings on the device, partitioned by confirmed owner. Cloud progress carries game state and stable entity identity with fallback display labels. Build on B1's timestamp, hydration and recovery behavior; preserve its four specifically approved legacy timestamp differences without creating further save-loss exceptions. Part A follows C because its notice depends on this behavior. No production deletion, migration, VACUUM, backup change or new cloud export is authorized by this plan.

2. Ownership and storage

Reuse ownerKeyFor, with separate unresolved, confirmed guest and confirmed account states. Never call an unresolved session a guest. A generation token changes immediately on session changes, sign-out broadcasts and deletion. Hide the previous owner's words immediately; check generation and captured owner after every await and before publishing results. Capture the legacy owner marker before any progress hook can update it. A missing original marker identifies legacy guest data; it does not grant an authenticated player ownership automatically.

Use one small local-word service with typed per-game accessors and a transactional IndexedDB store. The logical namespace remains hh-words:v1:<ownerKey>; final records use owner/app/entity/field keys, not one read-modify-write JSON document. An atomic transaction merges only its affected fields and commits a migration receipt. Pending records are independently keyed by captured owner, source key, schema version and source-content digest. Store original bytes when necessary for recovery. Do not overwrite or delete the whole pending collection. Known-owner records survive guest and other-account sessions, inaccessible until the recorded owner returns.

Sign-out retains owner partitions. Storage failures keep current edits in memory and display a persistence failure; do not claim those edits survive reload. Existing durable source data is never removed on that basis. No save timeout or artificial size/refusal gate is added.

4. Durable migration and global clearing

  1. At application bootstrap, enumerate every legacy word-bearing storage key without importing or visiting its game. Capture source bytes and the existing owner marker. Route every hydration replacement, sign-out clear and foreign-owner clear through this same migration coordinator.
  2. Commit an owner-tagged pending source in IndexedDB and verify transaction completion before allowing the original source to be stripped or removed. Commit final field records and their exact receipt atomically; retire only the corresponding pending record after that commit. Replaying the same source is idempotent. Changed source bytes produce a distinct version; do not retire an intervening writer's data.
  3. Before deleting or replacing a legacy localStorage key, compare its current bytes with the captured source. If they changed, capture the new version first. For concurrent tabs, use a per-source cross-tab lock for capture and replacement; ordinary word writes use IndexedDB transactions. A client unable to participate must preserve the legacy source rather than perform destructive migration. Do not infer that an old tab has stopped writing.
  4. Quota, denied storage, interrupted transactions or crashes leave the original source and its original ownership association intact. Authentication sign-out still proceeds, but clearing skips uncommitted sources. All new-client hydration/read/write paths must quarantine those keys from other owners; the ownership marker cannot be reassigned while it is needed to identify an uncommitted source. Unrelated gameplay may continue; never expose retained foreign bytes. A later successful migration can release the source safely.
  5. Test global sign-out from Home without opening any affected game. Test failures before pending commit and before final commit, then reload and sign-out. Test simultaneous different-app migrations, changed source versions and account A to guest/B to A.

Old tabs cannot be made to follow new client code. The rollout must explicitly test mixed versions and avoid claiming universal local preservation across an old client's destructive sign-out. The cloud preservation prerequisite below must also be satisfied before claiming recovery remains available until retirement.

5. Server boundary and legacy cloud recovery

Required release prerequisite: an ordinary sanitized POST must preserve the previous cloud words before replacing them. The split cloud preservation plan now has a passed focused design review: immutable owner-bound snapshots in the same transaction, matched-owner recovery, and an atomic compatible-writer cutover. PR80 (ea997a3) implemented and deployed this compatibility prerequisite with the additive schema and PostgreSQL evidence. Sanitization remains disabled. Client integration, recovery proof and exact production cutover authorization are still required before enabling local-only persistence.

One pure shared sanitizer removes every listed field before validating an incoming old-client upload, before reconciling an existing stored row, and from every ordinary progress response: per-app GET, aggregate GET, revision 409, strict ACK and fallback branches. Preserve non-word progress and B0 field rules. Keep revision tokens tied to the actual row version. Never log typed values in validation errors. Exercise seeded old rows through the real routes, including keepExisting and strict conditional paths.

Local migration alone cannot recover cloud-only words. Leave existing production rows and backups intact pending an explicit recovery design and deletion decision. Ordinary progress reads after C sanitize these words, so before that release provide a separately reviewed, authenticated legacy-recovery path for the same owner only, with no cross-owner lookup, no new text collection, no cache, and no typed-value logs. It returns the pre-existing legacy fields plus row revision to the device's migration service. Publish only after generation/owner checks and durable commit. Exact revision receipts demonstrate capture for that row on that device, not on every device or for every account.

The recovery path is a transitional exception for data already stored before C, not part of ongoing progress sync. Its access checks, retirement and privacy wording need a focused review before release. No elapsed waiting period proves preservation. If a row has no capture evidence, the later approval must explicitly identify potential cloud-only loss; do not silently delete it or claim it was recovered. A destructive retirement decision remains pending.

6. Account deletion integration

Preserved Part A already calls forgetLocalWords(userId) before sign-out and has a clear/reload fallback. Retain that public helper API, replacing its current single-localStorage-key implementation with owner-bound deletion of final records, pending sources, migration receipts and legacy candidates. Include the old namespace for compatibility. Never derive the target from the newly active session after an await.

Use an owner deletion generation/tombstone checked within write transactions and by mounted tabs; invalidate visible state and broadcast immediately. A late migration or callback must not recreate deleted words. A failed sign-out does not undo deletion. A failed local deletion must not be described as success or as proof storage is empty: retain a retryable deletion state and explain the failure. Test A deletion while B signs in, late hashing, active tabs and storage failures; other owners and guests remain intact.

7. Separately authorized production retirement

Prepare reviewed SQL and scratch-database tests after the implementation exists. Clear only enumerated fields in app_progress, then verify a read-only typed-field count of zero. VACUUM FULL and CHECKPOINT are separate production actions requiring specific approval and operational review. A changed relation file number demonstrates a table rewrite, not erasure of all historical physical bytes, WAL, snapshots, backups or replicas. Reconcile backup/PITR retention with Part A's runbook and obtain exact authorization before any cleanup. The original plan's one-row count is a historical observation, not a current inventory.

8. Required evidence

  • Per-game legacy fixtures retain all local words and drawings for their owner, preserve timestamps and financial/game state, and exclude text from every upload.
  • Deferred owner hashing, auth loading, cross-tab sign-out, foreign-owner clearing, pending storage failures and reloads preserve the ownership boundary.
  • Migration transaction failures and competing writers never erase the last durable source. Browser tests include IndexedDB unavailable and quota failure, not just mocked success.
  • Canonical Oregon replacement does not guess identity or lose unmatched words; explicit recovery and new journeys remain separate.
  • All server response paths and old-client saves obey sanitization; recovery is authenticated and durable, and cannot claim universal capture. Specifically: an old-client POST before recovery must still permit authenticated recovery of the original pre-existing words afterward.
  • Deletion prevents late resurrection and exposes local deletion failure accurately.
  • Run focused tests during implementation, DCR on the frozen change, the required full gate before push, and one browser gate with desktop and emulated phone contexts. Production writes remain independently authorized.

2026-10-04 implementation split

The first slice adds an inert, independently tested foundation under lib/local-words: exact legacy envelopes, owner lifecycle, transactional records and tombstones, capture before replacement, and authenticated cloud candidate recovery. No runtime caller is enabled by this slice. Existing saving, sign-out, game display and production policy remain unchanged until the following integration slice connects bootstrap, storage adapters and the seven games. The original contract above remains the acceptance bar for Part C as a whole.

The foundation preserves candidate sources instead of guessing identity. Differing destination values retain the source for an explicit later choice. A deleted owner is permanently tombstoned in this database so a delayed caller cannot obtain a new epoch and recreate deleted words.

Client integration must pass desktop and actual connected iPhone SE dogfooding, including storage failures and shared-device transitions. Test destructive account actions with isolated synthetic accounts. Preserve the personal browser login and saves.

Owner-bound progress integration prerequisite

The next client integration replaces all 33 account-synced localStorage writers with owner namespaces. Each physical key is hh-progress:v2: plus the JSON tuple of owner key and original logical key. Its atomic envelope contains version: 2, ownerKey, logicalKey, and the original serialized Zustand raw envelope. Inner persist versions, projections and game timestamps retain their existing meaning. The original keys and hanks-hits-progress-owner marker become read-only provenance; sign-out retains partitions.

One document binds one confirmed owner. Dynamic routes import their own module before awaiting real store hydration; input is unavailable until the merge completes. Temporary auth loading suspends writes and cloud leases. Confirmation of the same owner preserves live stores and permits same-owner cleanup flushes without rehydrating over play. A different owner revokes the document and requires hard navigation. A persisted back-forward-cache restore revalidates the session before exposing personal state. A failed navigation leaves a Reload action.

Explicit guest sign-in creates a handoff. First-account binding and immutable candidate receipts survive reload; a later account cannot claim them. Recovery sources retain guest provenance. Word-bearing candidates wait for their game's normalization rule, then settle the original timestamp/checksum before stripping words. Ordinary games pass admitted non-word candidates through existing server merge rules before normal account reconciliation. Cookie Clicker keeps guest bakeries as explicit recovery choices under its revision journal. Acknowledgements require successful reconciliation and durable current-owner progress. This does not grant guest words to the account.

Malformed or future-format owner envelopes are preserved exactly in quarantine before replacement. Failed quarantine or progress writes retain the prior durable source and current in-memory play, with a visible storage limitation. No new save timer or artificial size gate is introduced. Unchanged complete persist projections skip redundant writes, including flat stores and persist-version changes.

Rollback: once this version writes namespaced guest or account progress, the rollback build must retain its namespace reader, ownership rules and compatible writer. A legacy-only binary cannot read new namespaced saves. Frozen originals do not establish full backward compatibility. Old unmodified tabs can still mutate or delete their own legacy keys.

Part C remains incomplete: this prerequisite does not enable local-word final-record projections for the seven games or the production sanitization policy. Those game, recovery, deletion, browser, and physical-device gates remain mandatory before cutover. The new prerequisite is under implementation review; no release or full-gate claim is made by this note.
