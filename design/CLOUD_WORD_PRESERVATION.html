Part C prerequisite: preserve existing cloud words before replacement

Status updated 2026-10-04: PR80 deployed the compatibility prerequisite and additive schema; its production policy remains disabled. The Part C client runtime is now integrated in a local draft candidate, with remaining browser and physical-device gates. This document retains the prerequisite contract and historical implementation receipt. It does not authorize a production policy switch, client deployment or historical-data purge.

The integrated Part C client must not be deployed while the policy is disabled. Its HTTP and beacon payloads already remove private words and artwork. In disabled mode, POST does not call preserveProgressWords before the upsert. A newer sanitized save can therefore overwrite the only cloud source before device recovery finishes. Keep the candidate draft-only until remaining browser/device proof, compatible-writer verification and exact coordinated cutover authorization are complete. Enable preservation through the policy barrier before serving any integrated client. Do not rely on a device recovery request winning this race, and do not add an acknowledgement gate or deadline to ordinary saves.

Outcome and boundaries

An old client can save before a device runs word recovery. That save must update game progress without destroying pre-existing recoverable words. New typed values in requests are stripped and never added to recovery storage after cutover. The transitional recovery store contains only values already persisted by the prior release. No claim that all users or devices have recovered them is made.

Storage contract

Add a separate PostgreSQL table, legacy_progress_words, with progress_id as a foreign key to app_progress.id ON DELETE CASCADE; source_revision, extraction_version, payload JSONB, and captured_at. The composite primary key is (progress_id, source_revision, extraction_version). Ownership and app identity come only from joining the parent app_progress row to the authenticated user. There is no caller-supplied owner or global archive-ID lookup. Payload contains only the reviewed legacy field inventory with existing entity identifiers, not a complete gameplay blob. Account deletion cascades through users to app_progress to the recovery row. Explicit deletion of cloud progress also removes its associated recovery row; ordinary save and device capture do not.

Keep immutable versioned snapshots. Exact source revision and extraction version deduplicate retries; never overwrite a previous candidate. The usual row produces one snapshot because post-cutover writers strip incoming words. Versioned records also preserve an unexpected second stored legacy source without discarding the earlier one. Such a source triggers a values-free rollout diagnostic. Recovery returns each distinct candidate so the device can preserve rather than guess.

Transaction contract after cutover

  1. Under the revision foundation's existing owner/app advisory transaction lock, read the current progress row and validate any conditional revision before changing anything.
  2. Extract legacy fields from the stored row only. Never extract them from the request. Before an upsert can remove or replace them, insert the durable recovery snapshot in the same database transaction.
  3. Sanitize both request and existing progress, validate and reconcile as normal, then write progress. Commit archive and progress atomically. If the database fails, both roll back, leaving the original source intact; retain the client's normal retry journal. Do not add a timeout, rate gate, payload refusal or capture-ack requirement to valid saves.
  4. Revision conflicts return sanitized data; keepExisting returns no progress payload. Neither performs a destructive write. All success, GET, aggregate and strict ACK paths sanitize ordinary responses. Recovery failure cannot change the canonical revision or game state.

Recovery contract

An authenticated no-cache GET resolves the app from the allowlisted route and owner from the server session. Require a captured expected-owner assertion in a request header, compare it with the authenticated session before querying, and return a mismatch without any words when they differ. The assertion never authorizes a lookup or selects its owner. The client additionally verifies its captured owner and generation before committing; an A page with B cookies must never persist B words into A storage. Do not place owner assertions or typed values in URLs or logs. It reads immutable archived candidates plus any still-present legacy source under a consistent database snapshot. Return candidates separately with source revision and extraction version; do not guess which journey or entity they belong to. Deduplicate exact same-source copies only. The client checks its owner generation, commits candidates to its local-word transaction, and may record a values-free capture receipt. A receipt neither deletes the cloud source nor proves recovery on other devices. No typed values appear in logs, URLs, analytics or ordinary progress responses.

Rollout contract

  1. Finish and land B1 first. Prepare additive schema migration, server tests and compatibility release. The migration and release each need the appropriate exact production authorization; no migration runs from application startup.
  2. Deploy a compatibility server with preservation/recovery code present but sanitizing replacement disabled. Verify every active writer is on that compatible version, including background jobs, and old processes are drained. Preserve the current behavior until this is proven.
  3. Enable sanitizing replacement only after schema, all-writer compatibility and recovery readiness are verified. The switch is a separately authorized production change. Requests from old browsers are handled by the compatible server; no browser acknowledgement gates saves. Make the cutover atomic with writes: compatible writers take a shared transaction advisory lock for the cutover policy, then their existing owner/app lock, and read the database policy row in a separate statement after acquiring the locks, under Read Committed isolation. Read the request body before entering this transaction. The separately authorized cutover takes the exclusive policy lock and flips that row. Thus pre-cutover writes finish before the switch commits, and subsequent writes read enabled mode; an in-flight request cannot later persist using stale disabled mode. Shared locks preserve normal save concurrency; no timeout or request refusal is added. Include the policy row in the additive migration. Old binaries that do not honor this lock must already be drained.
  4. After cutover, rollback targets only a preservation-capable server and never re-enables collection of incoming words. Do not roll back to a binary that can overwrite progress without the handoff. A failure to verify writer drainage blocks cutover, not ordinary pre-cutover saving.
  5. Client migration and local recovery ship with ordinary-response sanitization. Existing retained data remains clearly disclosed as transitional. Retirement of raw fields, archive rows, backups and PITR is a later separately approved operation. Waiting is not a capture proof.

Proof required before implementation can be called ready

  • Real PostgreSQL tests: old-client POST before recovery; replace/merge/conditional saves; two competing requests; failure after archive insertion but before progress commit; no-op and conflict; parent deletion races; archive foreign-key cascades.
  • Recovery of original words after a successful sanitized save, without newly submitted text entering any stored row or log.
  • Consistent recovery during concurrent first capture; no missing or cross-owner candidates, and replay idempotency. Specifically freeze the client session at A while server cookies authenticate B: the request must return no words and commit nothing to A storage.
  • Rollout simulation covering a legacy request in flight at cutover, app restarts and rollback to the compatible release.
  • Document all progress writers and test multiple distinct stored legacy versions and exact-source retry deduplication; never drop a prior snapshot.
  • Account and cloud-progress deletion remove recovery data while unrelated users remain untouched. Retention and physical-erasure claims are kept separate from SQL row removal.

Implementation and rollout receipt

The only application progress writer found in apps/web/src, apps/web/scripts and packages is POST /api/progress/[appId]. It now acquires the shared policy lock before the existing owner/app lock, then reads the policy in a separate statement. Incoming-body reading remains outside the transaction. Word extraction is version 1. Candidates retain field paths and existing IDs, with no invented match for legacy Oregon journeys. The new GET /api/progress/[appId]/legacy-words requires the session owner in x-hh-expected-owner, performs owner-bound lookups in a read-only Repeatable Read transaction, and uses private, no-store responses.

Migration packages/db/drizzle/0002_legacy_progress_words.sql adds two tables and one disabled policy row. It does not rewrite app_progress. The compatibility release required its separately approved application before server deployment, using one explicit transaction on a dedicated migration connection. PR80’s release receipt is the historical authority for that completed prerequisite; do not reapply this migration as part of the client integration. The migration sets LOCAL lock_timeout to 5 seconds and statement_timeout to 30 seconds for its DDL only. On contention, roll back the entire migration and retry later; do not let pending DDL queue behind old writers indefinitely. These settings end with the transaction and never limit application saves. Its earlier unapplied status was a planning-time observation, not a current production inventory; do not blindly apply pending migrations. Drizzle metadata generation is local only. Before cutover, the deployed compatibility release retains normal word behavior and does not collect snapshots on ordinary saves; this statement does not authorize serving the integrated client in disabled mode. During enabled mode, each changing save captures only the old stored source, strips both inputs and ordinary outputs, and commits archive plus gameplay atomically. A revision conflict or keepExisting outcome does not archive or overwrite the row. Recovery reads both archives and the current source, so unchanged/conflicting saves remain recoverable.
