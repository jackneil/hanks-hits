1. Goal and what exists today

Jack, 2026-10-01: "when i said share i really meant they could share to the leaderboard so other people on our website could see how they played and got their score".

Goal. A player who is on a leaderboard can attach a video of a run to their entry. Anybody who opens that leaderboard on hankshits.com can tap the entry and watch the run.

What exists today (research 2026-10-01, file:line evidence in the research report):

  • Clips are on in production (CLIPS_MODE=on). A clip is made and kept on the player's own device (OPFS or IndexedDB). "Share" opens the phone's share sheet. Nothing goes to the site. On the real iPhone SE, the game-over clip path works (4 of 4 runs, h264 1280x720 30 fps, AAC 48 kHz stereo, 3.6 to 4.8 MB for 22 to 30 s).
  • A leaderboard row is one best value for each (gaming profile, game, score type). It keeps no run, no run time and no history. A score is the best value in the synced progress, so the server cannot tell which run made it. Only signed-in players have rows. The public name is a made-up handle (for example ThunderHero89), never the account name.
  • All 13 clip games have a leaderboard: arkanoid, asteroids, blitz-bomber, bomberman, breakout, dino-runner, endless-runner, flappy-bird, hextris, hill-climb, math-attack, platformer, space-invaders. For 12 of them the board value is a per-run best. For platformer it is a sum of stars over many runs.
  • The 12 board games with no clips (2048, snake, cookie-clicker, trivia, monster-truck, four-wheeler-3d, oregon-trail, chess, checkers, quoridor, wordle, memory-match) need the DOM-replay engine (GAMEPLAY_CLIPS.html Phase 4) before they can make a clip. This spec makes them work the day they get clips, with no extra change.
  • Production today: 4 accounts (all Google sign-in), 25 leaderboard rows. Traffic is small, so a grown-up can check every video by hand.

2. Decisions

#DecisionWhy
D1Video, not a move-log replay. The entry carries an MP4 that the player's own device made.The clip system already makes the video on the device for all 13 games. A move-log replay needs a deterministic simulation for each game (physics games are not deterministic across browsers). The DOM games get video through Phase 4.
D2One clip for each player and game. The player picks the run at game over. The newest upload replaces the old one.A kid wants to show a fun run, not only the best one. One clip per entry keeps storage and review small. The label shows the run's own score, so a clip of a lower run never claims the board score.
D3No approval step. A clip is public as soon as the upload checks pass.Owner decision (Jack, 2026-10-01): "i definitely dont want to be in charge of approving stuff. they are just showing their game not even their own voice or anything. this is just video sharing of game play that is fine". The clip is game picture and game sound only (D7). Accepted risk: a forged client can send a valid MP4 with a picture that is not the game. The guards need nobody: sign-in, rate limits, the box checks (section 6) and the Report button (D8).
D4Upload through our server, play from the bucket. The server checks the bytes, then stores them. A viewer gets a short-lived signed link to the bucket.Checking before storing means a bad file never reaches the bucket. Playing from the bucket costs nothing for egress (Railway buckets: egress free) and does not send video through Cloudflare, whose terms limit video on the free CDN.
D5A new Railway bucket hanks-hits-clips in the storage project hanks-hits-storage, beside the ROM bucket.Same provider and billing as the ROMs. $0.015 per GB-month, free operations and egress.
D6The feature is off unless it is set up. It turns on only when the bucket settings are set. LEADERBOARD_CLIPS=off is the kill switch.A kid clone that is put online with no bucket shows no upload button and no broken player.
D7A clip is game picture and game sound only. No name is painted into it. The upload check rejects metadata boxes.This is already how clips are made (GAMEPLAY_CLIPS.html section 10). It keeps the video free of personal information.
D8Report hides at once; nobody has to review. Any viewer can report a video, and it is hidden at once. The player can put another run on the board. The owner can remove their own video. An optional admin list (ADMIN_USER_IDS) can remove any video from the viewer sheet, for an emergency only.Zero work for a grown-up, and a fast way to take a bad video down. Abuse of the report button costs only a hidden video.

6. Upload checks (server, before anything is stored)

  • Signed in. The feature is set up and not switched off. The game is clip-enabled and has a board. The Content-Type is the one a browser sends for a form (multipart/form-data; boundary=... and nothing more).
  • Rate limit in the database (not in memory): 10 uploads each day for each account, 1 at a time.
  • The player has a row on the game's board (the progress sync writes it; an upload never makes a gaming profile). With no row the answer is 409, before the body is read.
  • A place in the server's upload gate: 3 uploads at the same time, 1 for each network address. The body must arrive in 5 minutes, and after 15 seconds every 15-second window must bring 8 KiB a second, so a body that stops cannot hold a place. A form with more parts than its four fields is refused before the parse.
  • Size: at most 16 MiB. Poster: a JPEG of at most 64 KB, with APP1 to APP15 and COM segments removed by the server.
  • An ISO-BMFF box walk (no third-party parser): ftyp first; moov before mdat (fast start); exactly one video track, avc1; at most one audio track, mp4a; width and height from the capture presets (landscape 1280x720 or portrait 720x1280, or a size the capture code scales to); duration from 1 s to 61 s; no udta and no meta box anywhere. Anything else is rejected.
  • runScore is a finite number from 0 to the game's progress-schema bound, normalized like a board score.

The checks prove the format, not the picture. A forged client can still send a valid MP4 with any picture. That risk is accepted (D3); the Report button takes such a video down at once.

7. Report and removal (no review queue)

  • Nobody approves anything. There is no queue, no notification and no admin page (D3).
  • Report: any viewer, rate limited by IP. The clip is hidden at once. The player sees "Your video was hidden" once, and can put another run on the board.
  • Remove: the owner can take their video off at any time. An account on the optional ADMIN_USER_IDS list sees the same remove button on every video, for an emergency only.
  • Unsafe content (if it ever happens): for child sexual abuse material, the law (18 U.S.C. 2258A) requires a report to NCMEC after actual knowledge, and keeping the material for 1 year. The admin remove action has a "Keep for a legal report" choice that moves the objects to a private prefix with no public link, in place of a delete. The law does not require monitoring (2258A(f)).

Account deleted (by the 24-month rule of #42, or by request)The row by cascade; the objects by the sweeper within 24 hours

The sweeper runs on the retention schedule that #42 adds (instrumentation.ts). It deletes rows past their time and any bucket object with no row. Railway buckets have no lifecycle rules, so the app does this itself.

9. Privacy (COPPA)

  • A clip has no child's image or voice and no name, so it is not personal information by itself (16 CFR 312.2 (8)). It is stored with an account that has an email, so the operator holds it as part of that account (312.2 (11)), the same as progress today.
  • The public sees the made-up handle, the score and the video. There is no messaging, so the handle is not online contact information.
  • The clip is made by the game's own capture code, so it carries no image or voice of the child and no name (D7). No personal information goes public with it.
  • The privacy notice (#42) gets one more part: players can put a video of a game run on the leaderboard; it shows only the game picture and game sound; anybody can watch it; the retention times in section 8. Section 312.4(d)(2) requires the notice to say whether a child can make information public.
  • #26i (signup collects a child's email with no parental notice) is fixed in its own PR: Google sign-in that keeps only Google's subject id, no email form. It is not tied to this feature.

10. Security

  • The bucket is private. Only the server holds its keys. Every viewer link is signed and lasts 10 minutes.
  • Object keys are random ids. A listing of the bucket is never exposed.
  • The remove route checks the owner (the session's gaming profile) or ADMIN_USER_IDS on every request, with the same-origin check the site uses.
  • Uploads are bounded (size, count per day, one at a time, the upload gate, a moving rate floor) and checked before any write. Every request body on the site is read with a byte limit (src/lib/read-body.ts), also the Auth.js sign-in routes.
  • Logs are values-free: game id, status code, sizes. Never the user id, the handle or the bytes.
  • The S3 signing uses a small, pinned, dependency-free library (aws4fetch). It gets a supply-chain review (/lockdown) before the merge.

11. Cost

At 3.5 MB a clip: 1,000 public clips is 3.5 GB, about $0.06 a month on a Railway bucket. Egress from the bucket is free. Upload traffic into Railway is free. There is no human time in the loop.

12. Tests and verification

  • Unit: the box walker (good files from real device clips, and bad files: extra track, udta, wrong codec, no fast start, too long, truncated); score normalizing; rate limit; retention rules; admin authorization; the leaderboard API shape.
  • Integration: the routes against a local Postgres and a local S3-compatible server, including the CSP header.
  • Real data: the migration and the leaderboard API change against a clone of the production database (createdb -T style, local).
  • UI: /qa and the phone gate at the four phone sizes; the result-chip button, the viewer sheet and the admin page are touch-only reachable with 44 px targets.
  • Live: after the deploy, on the real iPhone SE: game over, Put it on the leaderboard, then watch it from another browser that is signed out. Report it, check that it is hidden, remove it. Read back the bucket object, the row and the public API at each step.
